模型仅权重就需要约 14GB，再加上 KV Cache 和激活值，总需求可能接近 16-18GB。</p><br><p>当遇到显存不足时，可以采取以下几种优化策略：</p><br><ol><li><strong>量化加载</strong>：使用 4-bit 或 8-bit 量化版本模型。通过 <code>bitsandbytes</code> 库或直接下载量化后的权重（如 GGUF 格式配合 llama.cpp，或 AWQ 格式配合 vLLM），可将显存占用降低 50%-75%，且精度损失极小。</li><li><strong>调整 KV Cache 策略</strong>：在 vLLM 中，可以通过 <code>--gpu-memory-utilization</code> 参数控制预分配的显存比例。默认通常为 0.9，若系统还有其他进程，可适当调低至 0.8 或 0.7，留出余量防止崩溃。</li><li><strong>限制并发与长度</strong>：减小 <code>--max-num-seqs</code> 和 <code>--max-model-len</code> 的值。减少同时处理的请求数和单个请求的最大上下文长度，能直接降低峰值显存需求。</li></ol><br><p>通过组合上述手段，即使是 12GB 显存的显卡，也能流畅运行 7B :8000<br></code></pre><br><p>如果有其他进程占用，要么杀掉该进程，要么在启动 vLLM 时更换端口（如 <code>--port 8001</code>），并同步修改客户端代码中的 URL。</p><br><p>其次是防火墙与安全组设置。虽然在本地 localhost 通信通常不受限，但如果服务绑定在 <code>0.0.0.0</code> 且通过局域网访问，需确保操作系统的防火墙允许该端口入站。Linux 下可使用 <code>ufw allow 8000</code> 开放端口。</p><br><p>最后是服务健康检查。在发起复杂请求前，先尝试用 <code>curl</code> 访问模型列表接口：</p><br><pre><code class="prism language-bash"><span class="token 提示词工程技巧与输出质量提升</h3><br><p>模型的表现很大程度上取决于我们如何提问。优秀的提示词（Prompt）能激发模型的潜力，而模糊的指令则可能导致胡言乱语。提升输出质量的几个核心技巧包括：</p><br><ol><li><strong>角色设定（Persona）</strong>：在 System Message 中明确赋予模型特定角色，如“资深 Python 工程师”或“严谨的法律顾问”，这能显著改变其语气和专业度。</li><li><strong>少样本学习（Few-Shot）</strong>：在用户消息中提供 1-2 个高质量的问答示例，让模型模仿格式和逻辑。这对于格式化输出（如 JSON、Markdown 表格）特别有效。</li><li><strong>思维链（Chain of Thought）</strong>：对于复杂推理任务，鼓励模型“一步步思考”。可以在提示词末尾加上“请先分析问题的关键点，再给出结论”，这样能大幅减少逻辑跳跃导致的错误。</li><li><strong>约束条件明确化</strong>：明确指出“不要做什么”，例如“不要使用外部库”、“回答限制在 200 字以内”。负向约束往往比正向描述更能规范输出边界。</li></ol><br><p>通过反复迭代提示词，你会发现同样的模型能产出截然不同的结果，这是成本最低的性能提升方式。</p><br><h3><a id="__171"></a>⑩ 生产环境部署注意事项与安全规范</h3><br><p>当从实验走向生产，稳定性和安全性成为首要考量。首先，切勿直接将推理服务暴露在公网。应在服务前端架设 Nginx 等反向代理服务器，配置 HTTPS 加密传输，并实施严格的 IP 白名单或 Token 认证机制。</p><br><p>其次，资源隔离至关重要。建议使用 Docker 容器化部署，将模型服务及其依赖封装在独立环境中，避免与宿主机其他应用产生冲突，同时也便于横向扩展。对于高并发场景，应配置负载均衡器，将流量分发到多个推理实例。</p><br><p>最后，内容安全过滤不可忽视。虽然模型本身经过训练，但仍可能生成不当内容。建议在输入端和输出端分别接入敏感词过滤模块，对用户输入进行预处理，并对模型输出进行合规性扫描。同时，建立完善的日志监控体系，记录所有请求和异常，以便在出现问题时快速追溯和审计。只有做好了这些防护措施，本地大模型应用才能真正安心地服务于业务。</p><br><br>
